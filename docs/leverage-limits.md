Leverage controls read CoinDCX's `dynamic_position_leverage_details` for the selected futures pair and margin wallet. Deprecated `max_leverage_long` and `max_leverage_short` fields are ignored, as specified in the [exchange API reference](https://docs.coindcx.com/). Missing or malformed tiers block preview and management rather than defaulting to 100×.

The trade ticket shows the instrument ceiling. Preview also checks each planned order's notional against the size tiers. Individual management uses the current position size; group management uses the lowest supported maximum among its positions. Typing, +/- controls and presets require whole-number leverage within that limit. Existing saved ticket values remain visible for correction instead of silently changing the trade.

Immediately before a live create or leverage update, the server reads fresh instrument rules. Creates include current position and reported pending entry quantities in the exposure check. Parallel group accounts share a public instrument read while it is in flight, without reusing a completed cached read at execution. Exits and reductions remain available when entry leverage limits change. Exchange validation remains authoritative for fills, balance availability and liquidation constraints.

Individual leverage management replaces the leverage range with an available-balance percentage range. It estimates required margin from quantity, entry price and the position's actual settlement FX. The target leverage rounds up to a whole number so estimated additional margin stays within the selected budget; unused balance remains visible. The range is disabled while balance refresh runs, when refresh fails, or when balance/collateral/FX/limits are unavailable. Group leverage management has no range. Amounts and liquidation prices remain estimates, since fees, funding and exchange recalculation can alter the final result.

Validation covers dynamic 20× metadata, deprecated-field rejection, exact tier boundaries, missing metadata, balance-budget rounding, individual/group controls, saved excessive values, stale coin selection, and production composition against an isolated fake exchange. No database migration is required.

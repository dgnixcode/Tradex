# Trading and security audit — 8 October 2026

This change fixes concrete money-loss and security defects found in the trading, position-management, authentication, strategy-execution, and static-file paths. The changes are local and have not been pushed or deployed. Production environment files, production databases, and live authenticated trading accounts were not used for testing.

## Findings and fixes

| Finding | Fix |
| --- | --- |
| Confirmation and queue insertion could commit separately, leaving confirmed orders without jobs or protection siblings. | Confirmation, entry jobs, and SL/TP children now commit in one transaction. Concurrent confirmation has one winner. |
| Workers claimed jobs of the wrong kind before filtering them, stranding work. | Place and resolve jobs are filtered during the atomic database claim. |
| Old unresolved orders stopped blocking new orders. Partial fills could be considered complete. | Unresolved and partially filled orders continue to block competing sends regardless of age. Group completion waits for their resolution. |
| Order age, an existing position, or an empty read-back could be mistaken for a fill/non-placement. | Resolution uses the recorded venue ID, or a unique exact-decimal match within the actual send window. Absence and ambiguous matches require reconciliation. No blind resend. |
| Separate tabs/processes could adjust or exit the same position concurrently. | Durable action receipts and database locks exclude concurrent actions on one account/pair. Reusing a UUID replays its result; changing its payload is rejected. Unknown outcomes retain the lock. |
| Browser connection queues and small frontend pools staggered group position actions. | The browser batches up to 100 actions in one request; the server dispatches distinct accounts concurrently and returns individual results. The exchange socket pool allows 128 connections. |
| Preview budgets could race; leverage and currency changes could bypass daily margin limits. Direct increases bypassed those limits. | Preview reservations and direct increases share a transaction-scoped budget lock. Daily spend uses each trade's leverage, converts currencies explicitly, counts direct-action reservations, and avoids counting their audit rows twice. Missing FX/rules fail closed. |
| Floating-point rounding could change reduce quantities, venue read-back values, or recorded notionals. | Quantities, step/tick validation, risk amounts, and direct-order notionals use integer decimal arithmetic. Futures quantities remain exact JSON numbers when signed/sent; numeric venue values are parsed without floating-point rounding and exponent notation is normalized. Oversized reductions are floored safely; full reductions use the verified exit sequence. Missing remaining-quantity evidence no longer invents a full fill. |
| Automatic protection calls omitted tenant context. Pending-limit cancellation was not wired to the server adapter. | The signer receives the correct tenant and account. Protection changes use position locks and retain venue order IDs. Pending limits can be cancelled and verified through exchange read-back. Partially cancelled entries also receive protection. |
| Protection replacement could proceed after an unreadable/failed cancellation. | Failed reads/cancellations abort replacement or exit. Uncertain attachment outcomes retain the exclusion lock for review. |
| Trailing stops assumed a long position, reused stale prices, used floating-point prices, and could overlap across workers. | Long and short trailing calculations use exact decimals and current ticks. Fresh per-pair prices, atomic claims, and overlapping-loop prevention protect updates. Failed updates are marked failed rather than blindly repeated. |
| User scripts received Node VM host objects and could escape into server capabilities. | Scripts run in QuickJS WASM with JSON-only SDK boundaries, memory/CPU/time/data/call limits, and bounded indicator inputs. Started trades finish before a strategy lease is released, including after guest timeout. Cross-process strategy leases prevent duplicate scheduled cycles. |
| Static URL traversal could access files outside the web build. Historical-data paths also accepted unsafe components. | Static paths are confined to the build directory; candle symbols, timeframes, dates, and resource limits are validated before filesystem access. |
| Forwarded login IPs were trusted without checking the proxy. Concurrent failures could evade the block threshold. | Only explicitly trusted immediate proxies can supply client IPs; failure counters and blocking are atomic. |
| Cross-site mutations, unreleased sessions, and password recovery weakened account security. | Origin/fetch-site and JSON content-type checks, security headers, logout/impersonation session revocation, single-use recovery tokens, user-level recovery locking, fixed recovery origins, and removal of reset-token logging. |
| Live trading could start with fixture prices or a public development encryption key. | Live-money startup requires live books, explicit private key configuration, HTTPS application origin, persistent cookie secret, secure cookies, and authenticated signer configuration. Signer mutation detection inspects nested order payloads before trusting descriptive text. |

Reviewed database paths use bound values through Kysely and parameterized SQL templates. No exploitable SQL-injection interpolation was found in the reviewed paths. Request validation rejects malformed trade inputs before planning side effects. This is a code audit and regression test effort, not a certification that every possible attack has been eliminated.

## Production rollout

1. Back up the database and current application/configuration. Rehearse the release on a staging copy, including existing accounts, groups, custom strategies, and open/partially filled orders. Schedule a controlled trading pause for migration/deployment and let active requests drain. Keep an independent exchange session available for managing open positions.
2. Check configuration **before** replacing running processes. `APP_URL` must be the public HTTPS origin. Preserve the existing private `TRADEX_LOCAL_ROOT_KEY`, cookie secret, execution pepper, and credential pepper. Set the same random signer token of at least 32 characters on API and signer. Real sending requires `TRADEX_LIVE_BOOK=1`. Configure `TRADEX_TRUSTED_PROXY_IPS` with the exact immediate proxy IPs if a reverse proxy supplies client IPs. Production cookies are now always Secure.
3. **Never replace an existing encryption root key blindly.** If the current deployment used the public development key, pause and arrange a controlled credential/TOTP key migration or reconnect/re-enrolment before this release. Simply changing the variable makes existing encrypted records unreadable. The new startup guard intentionally refuses the public key. A managed KMS with separate IAM permissions remains a deployment requirement for stronger secret isolation; this repository still uses its explicitly opted-in LocalKms implementation.
4. Apply forward migrations **035_position_mutation_safety** and **036_roe_decimal_storage** with the existing migration runner before starting the new API/workers. 035 adds receipts, send timestamps, audit links, and strategy leases. 036 converts the historical ROE presentation column to text; the reader continues returning a numeric percentage. Allow a maintenance window for its table lock/rewrite. No historical migration checksum is changed.
5. Install the locked dependencies and rebuild the application; the release must include the new QuickJS runtime and its WASM assets. Deploy compatible API, workers, and signer together, then deploy the frontend. Do not mix older workers with newer concurrency/reconciliation rules while trading is enabled. The frontend batch endpoint requires the new backend. Rehearse market/limit, group/individual, cancel, SL/TP, add/reduce, exit, and retry flows in staging first.
6. Validate custom strategies before resuming schedules. JSON-compatible SDK calls remain supported; Node globals/imports and host-object tricks are intentionally unavailable. Mixed INR/USDT wallets must select `params.marginCurrency`; opposing group positions must be inspected through `positions.list()`. Guest resource limits and backtest limits can reject previously unbounded scripts.
7. Resume with a controlled canary and monitor exchange rejects, partial fills, unmatched orders, retained action locks, failed trailing stops, strategy leases, and per-account dispatch/ack/fill timings. Retain the database migrations and receipts on an application rollback; do not roll back evidence of possibly sent orders. An older worker release does not preserve these safety guarantees, so keep trading paused until reconciliation and a compatible release are ready.

## Uncertain-action recovery and practical limits

`position_mutation.status = 'sending'/'needs_review'` and `algo_strategy.execution_token IS NOT NULL` after a crash are operator-review states. Check exchange order history, positions, conditionals, quantities, timestamps, and action receipts. Confirm that the originating process has stopped and no request is still in flight. Reconcile the outcome and audit it before marking a receipt completed/releasing its exact account/pair/request lock or clearing a strategy lease. **Do not delete receipts, shorten the timeout to unlock them, or retry with a fresh UUID to get around a pending action.** There is deliberately no automatic resend or automatic unlock of uncertain mutations.

Concurrent dispatch does not mean atomic exchange execution. The exchange can accept/fill accounts at different times, reject some accounts, throttle requests, or leave limit orders resting/partially filled. No live sub-second latency claim has been measured or guaranteed here. Record send-start, acknowledgement and fill timestamps under the actual production account count before setting a latency objective.

SL/TP attachment is a separate exchange operation after an entry fill is observed. A partially filled resting limit can therefore have temporary unprotected exposure until the entry finishes or is partially cancelled and protection is attached. This release does not provide a native atomic bracket guarantee. Protection replacement also has a cancel/create interval. Trailing protection requires a running healthy service and fresh prices.

Application locks cannot prevent manual trades, liquidation, or other external software from changing a position between its read and a reducing order. The venue does not provide a guaranteed reduce-only primitive in this integration; unsupported reduce-only entry requests are explicitly refused. Full closes use the venue exit operation, cancel stale conditionals first, and verify flat. Remaining native-exchange limitations require operational monitoring and exchange-side protection where available.

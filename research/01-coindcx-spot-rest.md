# 01 - CoinDCX spot REST contract

Status: 2026-09-03 | track: exchange ground truth | scope: the complete, verbatim request/response contract for CoinDCX spot REST (public market data, user, wallet transfer, all 11 spot order endpoints, Lend/funding) as the single source of truth for every other Tradex document.

## Verdict

- **Sizing by money is not a CoinDCX feature.** `orders/create` accepts `total_quantity` only - a quantity in the *target* asset. There is no quote-notional order parameter anywhere in the spot API. Every "buy Rs 20,000 worth" and every "20% of allocated capital" must be converted to a quantity **by us**, against a price **we** choose, and then legalised against 5 independent per-market constraints. This is the highest-risk arithmetic in the product and it lives entirely on our side of the boundary.
- **`client_order_id` is a real idempotency primitive and we must use it on every order.** It is accepted on create and is a first-class lookup key on `orders/status`, `orders/status_multiple`, `orders/cancel`, `orders/cancel_by_ids` and `orders/edit`. Docs state reuse is *rejected*, so a retry cannot double-place. Rule: never blind-retry `create`; on any ambiguous outcome, resolve by `orders/status` with the same `client_order_id`.
- **There is no group-atomicity and no cross-account batching.** `orders/create_multiple` batches up to 10 orders for **one** API key, INR markets only (`ecode: "I"`). A group trade over 20-100 accounts is N independent signed HTTP calls. Partial group failure is therefore structural, not exceptional - design it in from day one (see `08-fanout-execution-engine.md`).
- **CoinDCX inverts the industry's base/quote naming.** `base_currency` = the *pricing* asset (INR, USDT). `target_currency` = the asset you are buying. So `base_currency_precision` is *price* precision, `target_currency_precision` is *quantity* precision, and `min_notional` and `fee_amount` are in INR/USDT. Getting this backwards silently mis-sizes every order.
- **There is no spot order-history endpoint.** Only `active_orders` (per market, market is *required*), `status`/`status_multiple` (by id, max 10) and `trade_history` exist. If we lose our own record of an order, the exchange offers no way to enumerate it. Our order log must be durably written **before** the create call, and `orders/trade_history` (which accepts no market filter) is the only global divergence detector.
- **Charting off the documented spot candles endpoint is not viable.** `market_data/candles` accepts exactly `[1m, 15m, 1h, 1d]` - verified live from the API's own 422 message. An endpoint on `public.coindcx.com` **does** serve spot pairs at nine resolutions and accepts a `from`/`to` window (verified live: `1, 5, 15, 30, 60, 240, 480, 1D, 1M, D` accepted; `3, 7, 120, 720, 1W, W, 1440` rejected - so it is a **fixed whitelist, not arbitrary resolutions**, correcting an earlier claim in this file). It is documented only for futures and carries no compatibility promise for spot. `13-charting-live-market-data.md` owns this fork and `03-coindcx-futures-orders-rest.md` F9 has the full probe record.

## Decisions

| Decision | Choice | Why | Rejected alternative |
| --- | --- | --- | --- |
| Order identity | `client_order_id` generated by us, globally unique, <=36 chars, recorded before send | Only server-side dedupe primitive available; also the only key that survives a lost HTTP response | Rely on exchange `id` from the create response (unavailable exactly when you need it - on timeout) |
| Retry policy on create | Never retry create. Resolve by `orders/status` on `client_order_id`, then decide | Docs promise duplicate `client_order_id` is rejected, but the rejection is indistinguishable from a validation rejection; only a status lookup is authoritative | Retry with same id (relies on undocumented error discrimination); retry with a new id (duplicates real money) |
| Request body construction | Hand-build the JSON body string from decimal strings; sign those exact bytes; send as a raw string | HMAC is over the raw body, so re-serialisation by an HTTP client is a correctness bug. Hand-building also means no value ever passes through a float | Pass an object to the HTTP client and hope its serialiser matches the signed string |
| Money representation | Decimal strings end to end; emit JSON numeric literals verbatim from those strings; never a JS `number` | Live responses contain values like `82032.93333333333` and `0.00000001`; INR prices carry 1-2 dp, quantities up to 8 dp | Integer minor units (breaks down for 8-dp crypto quantities against a 2-dp INR price in the same expression) |
| Market identifier for orders | `coindcx_name` (e.g. `BTCINR`) in the `market` param | Verified unique across all 999 live markets, and the only form the order endpoints accept | `symbol` (differs from `coindcx_name` on 284 markets); `pair` (market-data/socket namespace only) |
| Timestamp unit | Epoch **milliseconds** | Every official code sample uses `time.time()*1000` / `Date.now()`; the prose and the parameter tables contradict this and are wrong | Seconds, as the parameter-table examples and the wallet-transfer prose claim |
| Market-order availability | Refuse a MARKET intent on a market whose `order_types` omits `market_order`; never substitute | 328 of 999 live markets are limit-only, including INR pairs | Silent substitution with an aggressive limit order (changes the trade the user asked for) |
| Time in force | Do not send `time_in_force` on spot; assume `good_till_cancel` | Docs: spot "just contains one value for now, which is good_till_cancel"; it is a response field, absent from every request table | Send `immediate_or_cancel` (exists only for futures) |
| Reconciliation spine | `orders/trade_history` with `sort: asc` + `from_id` cursor, no `symbol` filter, per account | Only account-wide, monotonic, cursored feed in the spot API; catches fills of orders we do not know about | Poll `active_orders` per market (requires knowing the market; 999 candidates; silent on filled orders) |
| Rate budget | Self-imposed token bucket at 16/s and 960/min per API key, plus 30/60s for `cancel_all` and 300/60s for `active_orders` and `cancel_by_ids` | Two conflicting documented limits; engineer to the tighter of them | Trust the `ratelimit` response headers (absent on authenticated routes) |

## Findings

Tags: **V-doc** = read in the local docs file (line refs given). **V-live** = observed by me against the live API on 2026-09-03 (unauthenticated public routes only). **UNVERIFIED** = inference, or documented-but-untested; each carries the experiment that would settle it.

### F0. Terminology - read this before any arithmetic (V-doc, lines 551-563)

Verbatim: *"target currency refers to the asset that is the quantity of a symbol"*; *"base currency refers to the asset that is the price of a symbol"*; *"pair uniquely identifies the market along with its exchange"*.

| CoinDCX word | Industry word | For `BTCINR` | Consequence |
| --- | --- | --- | --- |
| target currency | base asset | BTC | `total_quantity` is in BTC. `target_currency_precision` is QUANTITY precision. `step` is a QUANTITY increment. |
| base currency | quote asset | INR | `price_per_unit` is INR per BTC. `base_currency_precision` is PRICE precision. `min_notional` is in INR. `fee_amount` is in INR. |

Do not name any Tradex type `baseCurrency` after CoinDCX's meaning. Name them `quoteAsset` / `tradedAsset` at the adapter boundary and translate once, in one function.

### F1. Hosts, transport, authentication (V-doc, lines 539-547, 1278-1402)

| Item | Value |
| --- | --- |
| Primary host | `https://api.coindcx.com` (all spot endpoints, public and authenticated) |
| Secondary host | `https://public.coindcx.com` - *"only be used where it is exclusively mentioned"*; no documented spot endpoint uses it |
| Public endpoints | HTTP GET, query params, no headers |
| Authenticated endpoints | **all POST**, all parameters as a JSON body, no query params |
| Required body param on every authenticated call | `timestamp` |
| Signature | `signature = HMAC-SHA256(message = exact JSON body, key = api-secret).hexdigest()` |
| Headers | `X-AUTH-APIKEY: <key>`, `X-AUTH-SIGNATURE: <hex>`, `Content-Type: application/json` |
| Timestamp validation | *"the request is rejected with an appropriate error if this timestamp deviates too much from the server's time"* - the tolerance is **not quantified** anywhere (UNVERIFIED; experiment: send `timestamp` at now-30s, now-120s, now+120s on `users/balances` and record the first rejection) |

Signing notes that are load-bearing:

- The Python sample signs `json.dumps(body, separators=(',',':'))` - compact, no spaces - and posts that exact string. The JavaScript sample signs `JSON.stringify(body)` and then hands the **object** to `request` with `json: true`, relying on the library re-serialising to a byte-identical string. That works by accident of key insertion order. Build the string once, sign it, send it. (V-doc, 1291-1401)
- Key **order** in the JSON is irrelevant to the server (it verifies the HMAC over raw bytes, then parses) but must be identical between signing and sending.
- There is no nonce and no request id. `timestamp` plus `client_order_id` are the only replay controls.
- **API keys cannot be scoped.** FAQ verbatim: *"Are there Read Only APIs available... No, we currently don't have Read Only APIs"* and *"all API users have the same level of permissions, API keys are interchangeable"*. The only hardening is optional IP binding at key-creation time (V-doc 669-675, 13912-13919). See 07-api-key-security.md.
- No crypto-withdrawal endpoint exists in this API surface (grep: zero withdrawal endpoints across the whole docs file). A leaked spot key can trade and can move funds between the user's own spot/futures wallets and between master and sub-accounts, but cannot documentedly withdraw off-platform. V-doc by absence; UNVERIFIED as a security guarantee.

### F2. Rate limits - three conflicting numbers

| Source | Claim |
| --- | --- |
| Per-endpoint table (V-doc 715-765) | create 2000/60s, create_multiple 2000/60s, status 2000/60s, status_multiple 2000/60s, cancel 2000/60s, edit 2000/60s, **cancel_all 30/60s**, **cancel_by_ids 300/60s**, **active_orders 300/60s** |
| FAQ (V-doc 13922-13924) | *"16/sec, 960/min"* |
| Live response headers on public routes (V-live) | `ratelimit-policy: 5000;w=60`, `ratelimit: limit=5000, remaining=4996, reset=16` |

Reading: 960/min is the per-key global ceiling (16/s is its per-second shape); the 2000/60s per-endpoint numbers cannot all be spent simultaneously; 5000/60s is a gateway/IP limit seen only on public routes. The authenticated 401 response carried **no** `ratelimit` headers (V-live), so we cannot meter authenticated routes from headers.

UNVERIFIED and it matters for a 100-account fan-out: are authenticated limits per API key or per source IP? Experiment: two accounts' keys from one IP, drive 20 req/s of `users/balances` on key A, then check whether key B starts receiving 429. If the limit is per-IP, fan-out throughput is capped globally and needs an egress pool.

Infrastructure observed (V-live): Cloudflare in front of Kong (`via: kong/3.4.2`, `x-envoy-upstream-service-time`). `/exchange/ticker` returned `cf-cache-status: HIT` - it is CDN-cached and therefore stale by an unknown amount. Every other endpoint returned `DYNAMIC`. **Never price an order off `/exchange/ticker`.**

### F3. Identifier namespaces - four of them, and they do not interchange (V-live over all 999 markets)

| Identifier | Form | Example | Accepted by |
| --- | --- | --- | --- |
| `coindcx_name` | `TARGET` + `BASE`, concatenated | `BTCINR`, `BTCUSDT`, `LYXUSDT` | the `market` param of every order endpoint; `symbol` filter of `orders/trade_history`; `market` field of `/exchange/ticker` |
| `pair` | `ECODE-TARGET_BASE` | `I-BTC_INR`, `B-BTC_USDT`, `KC-LYX_USDT`, `G-BONE_USDT` | `market_data/*` (trades, orderbook, candles) and the sockets |
| `symbol` (in `markets_details`) | upstream venue symbol | `BTCINR` (I/B) but `LYX-USDT` (KC) and `BONE_USDT` (G) | nothing - it is metadata. **Never send it.** |
| `ecode` | `I`, `B`, `G`, `KC` | `I` | required by `orders/create_multiple` only |

Verified derivations, zero exceptions across 999 markets (V-live):
- `pair == ecode + "-" + target_currency_short_name + "_" + base_currency_short_name`
- `coindcx_name == target_currency_short_name + base_currency_short_name`
- `coindcx_name` is **unique** (0 duplicates) - safe as our primary key
- `symbol != coindcx_name` on **284 of 999** markets: all 244 `KC` markets (hyphen form) and all 40 `G` markets (underscore form)

**`source`** on an order object: only `web` is ever shown, in every sample, including samples of API-created orders. UNVERIFIED what value an API-placed order carries. This matters - if it differs, `source` distinguishes Tradex orders from the customer's manual web orders during reconciliation. Experiment: place one order via API on a test key and read back `source` from `orders/status`.

### F5. Public endpoints

#### F5.1 `GET /exchange/ticker`

No parameters. Returns an array of one object per market (999 live).

| Field | Kind | Type | Meaning |
| --- | --- | --- | --- |
| `market` | identity | string | `coindcx_name`. **No `pair` and no `ecode` field** |
| `last_price` | PRICE | **string** | last traded price, base per target |
| `bid` | PRICE | **string** | *"Highest bid offer in the orderbook"* |
| `ask` | PRICE | **string** | *"Highest ask offer in the orderbook"* - reads "highest" in the docs; it is the lowest ask (V-live: BTCINR bid 8004981.9 < ask 8035000) |
| `high` / `low` | PRICE | **string** | 24h high / low |
| `volume` | QUANTITY | **string** | *"Volume of the market in last 24 hours"*; unit (target vs base) not stated - UNVERIFIED |
| `change_24_hour` | RATE | **string** | percent; live values carry up to 16 significant digits (`"4.8239444346208688"`) |
| `timestamp` | time | number | **SECONDS**, not milliseconds |

- The docs say *"timestamp - Time when this ticker was generated(in milliseconds)"* and the sample shows a 13-digit value (V-doc 806, 828). Live returns 10 digits: `1788457764` = 2026-09-03T17:49:24Z. **The docs are wrong; it is seconds.** (V-live)
- *"A ticker is generated once every second"* (V-doc 830), but the response is CDN-cached (`cf-cache-status: HIT`, V-live). Unusable as a pricing source.
- All numeric fields are strings with inconsistent decimal formatting in the same payload: `"8035000.0000000000"`, `"8039999"`, `"7609772.2"`. Parse with a decimal library.

#### F5.2 `GET /exchange/v1/markets`

No parameters. Returns a flat array of `coindcx_name` strings. 999 live, same count as `markets_details`. *"Returns an array of strings of currently active markets."* (V-doc 866-873). Strictly a subset of `markets_details` information - no reason for Tradex to call it.

#### F5.3 `GET /exchange/v1/markets_details` - the sizing rulebook

No parameters. Array of 999 objects live. This endpoint is the input to every legality check; cache it and refresh on a schedule.

| Field | Kind | Type (live) | Meaning (V-doc 944-1016) / live notes |
| --- | --- | --- | --- |
| `coindcx_name` | identity | string | the `market` param for orders |
| `symbol` | identity | string | upstream venue symbol; **not** an order param |
| `pair` | identity | string | *"created by (ecode, target_currency_short_name, base_currency_short_name)... For example: B-BTC_USDT, I-BTC_INR, KC-XYZ_USDT"* |
| `ecode` | enum | string | `I` / `B` / `G` / `KC` |
| `status` | enum | string | *"active or inactive"* |
| `target_currency_short_name` | identity | string | asset being traded (BTC) |
| `base_currency_short_name` | identity | string | pricing asset (INR / USDT / BTC / ETH / USDC / TRX) |
| `target_currency_name` / `base_currency_name` | label | string | display names |
| `target_currency_precision` | PRECISION (quantity) | integer | *"Number of decimals accepted for the target currency"*. **0 on 284 markets** = integer quantities only |
| `base_currency_precision` | PRECISION (price) | integer | *"Number of decimals accepted for the base currency"*. BTCINR 1, USDTINR 2, BTCUSDT 2 |
| `min_quantity` | QUANTITY | number | *"minimum quantity of target currency for which an order may be placed"*. Can be `0`; smaller than the precision floor on 299 markets |
| `max_quantity` | QUANTITY | number | max for a **limit** order |
| `max_quantity_market` | QUANTITY | number | *"Maximum quantity allowed for market orders"* - a **separate, far tighter cap**: BTCINR `max_quantity` 2 but `max_quantity_market` **0.0158** |
| `min_notional` | NOTIONAL | number | *"minimum amount of base currency for which an order may be placed"*. **Rs 100 on all 339 INR markets**; USDT markets mostly 5 |
| `min_price` / `max_price` | PRICE | number | *"minimum/maximum Price for which an order may be placed"*. On INR markets these are dynamic bands around spot (BTCINR 3,511,201 .. 31,600,800). Live values include repeating decimals: ETHINR `min_price: 82032.93333333333` |
| `step` | QUANTITY increment | number | *"minimum increment accepted for the target currency"*. **Not always 10^-precision** |
| `order_types` | enum array | string[] | *"Different type of orders that can be placed for the market"* |
| `max_leverage` / `max_leverage_short` | RATE | number / null / **absent** | margin only. `null` on 704, `0` on 255, **key absent on all 40 `G` markets** |
| `bo_sl_safety_percent` | RATE | number | *"Safety buffer percentage for bracket/stop-loss orders"*. Live: 1 (975), 0.1 (21), 0 (3) |

Live market universe, 2026-09-03 (V-live):

| Cut | Count |
| --- | --- |
| markets total (all `active`) | 999 |
| by `ecode` | B 376, I 339, KC 244, G 40 |
| by pricing asset | USDT 626, INR 339, BTC 27, ETH 5, USDC 1, TRX 1 |
| **without `market_order`** | **328** (includes INR pairs: IMXINR, NKNINR, XAUTINR, BSVINR, MOODENGINR) |
| `target_currency_precision == 0` | 284 |
| `min_quantity < 10^-target_currency_precision` | 299 |
| `step != 10^-target_currency_precision` | 7 - BNTINR (step 0.1, precision 2), SAPIENINR (0.001, 1), XDCINR (0.01, 4), NIBIINR (0.0001, 0), WENINR (1e-7, 4), DEFIINR (1e-7, 0) |
| INR markets with `min_notional != 100` | 0 |

The five constraints an order must satisfy simultaneously - all from this one endpoint:

1. `order_type` present in `order_types`
2. quantity >= **max(`min_quantity`, 10 to the power -`target_currency_precision`)** - the FAQ states this explicitly (V-doc 13984-13988): *"if the min_quantity returns 0.0001 and the target_currency_precision is 2, then the min quantity allowed is actually 0.01"*
3. quantity <= `max_quantity` (limit) or <= `max_quantity_market` (market)
4. quantity is an exact multiple of `step` **and** carries no more decimals than `target_currency_precision` - these are independent, see the 7 mismatched markets
5. quantity * price >= `min_notional`, and price within [`min_price`, `max_price`] with at most `base_currency_precision` decimals

Constraints 2 and 5 collide in exactly the way Tradex percentage sizing will hit it. On BTCINR, `min_notional` Rs 100 at ~Rs 8,000,000/BTC needs 0.0000125 BTC, but `target_currency_precision` 5 forces a 0.00001 grid, so the smallest legal order is 0.00002 BTC = Rs 160. A 20% allocation on a small account can land between the two and must be refused or rounded up - a product decision, see Open questions.

#### F5.5 `GET /market_data/orderbook`

| Param | Required | Type | Allowed / default |
| --- | --- | --- | --- |
| `pair` | Yes | string | `pair` form |
| `depth` | No | integer | default 50; **exactly** `[1, 5, 10, 20, 50, 100, 200]` (V-live 422 enumerates them). Docs table capitalises it `Depth`; lowercase `depth` works (V-live) |

Response: `{ timestamp, bids, asks }`.

- `timestamp` is **milliseconds** here (V-live 1788457390393) - unlike `/exchange/ticker`, which is seconds.
- `bids` and `asks` are **JSON objects keyed by price string**, not arrays: `{"8037392.2000000000":"0.000072", ...}`. Values are quantity strings. Live keys carry 10 decimal places regardless of `base_currency_precision`.
- Live ordering was asks ascending, bids descending, but **JSON object key order is not a contract**. Sort explicitly after parsing.
- FAQ: socket order books are 50-level snapshots; REST honours `depth` (V-doc 14030-14036, V-live).
- This is the correct source for a market-order reference price and for slippage estimation.

#### F5.6 `GET /market_data/candles`

| Param | Required | Type | Allowed / default |
| --- | --- | --- | --- |
| `pair` | Yes | string | `pair` form |
| `interval` | Yes | string | **exactly `1m`, `15m`, `1h`, `1d`** (V-live 422: *"interval must be one of [1m, 15m, 1h, 1d]"*) |
| `startTime` | No | integer | ms epoch. **camelCase** |
| `endTime` | No | integer | ms epoch. **camelCase** |
| `limit` | No | integer | default 500, **max 1000** (V-live 422 at 1001) |

Response: array of `{open, high, low, close, volume, time}`, all **numbers**, `time` = open time in ms, sorted **descending** by time (V-doc 1264, V-live).

- `volume` is *"total volume in terms of target currency"* (V-doc 1215).
- `5m`, `4h`, `1w` are all rejected (V-live). No other aggregation is offered.
- **Unknown query params are silently ignored, not rejected.** `start_time` (snake_case) returned the default 500 candles instead of the requested window (V-live). A param-name typo therefore yields plausible wrong data - our client must whitelist params and assert on the returned window.

#### F5.7 `GET https://public.coindcx.com/market_data/candlesticks` - undocumented for spot

Documented only under Futures (V-doc 8387-8394) but **verified live to serve spot pairs** at resolutions the spot endpoint refuses:

| Param | Required | Notes (V-doc) | Live behaviour for spot (V-live) |
| --- | --- | --- | --- |
| `pair` | Yes | *"Name of the pair"* | `I-BTC_INR` and `B-BTC_USDT` both returned real spot OHLCV |
| `from` / `to` | Yes | *"EPOCH ... in seconds"* | honoured |
| `resolution` | Yes | *"'1' OR '5' OR '60' OR '1D'"* | `5` and `15` both accepted - broader than documented |

Response `{"s":"ok","data":[{open,high,low,close,volume,time}]}`, `time` in **ms**, ascending. The only route to 5m/15m spot candles, but undocumented for spot, so no compatibility promise. Charting track owns whether to depend on it.

| Field | Kind | Type | Meaning |

| `currency` | identity | string | short name, e.g. `BTC`, `INR`, `USDT` |
| `balance` | QUANTITY | number | free balance |
| `locked_balance` | QUANTITY | number | *"the balance currently being used by an open order"* |

- Available = `balance`; total = `balance + locked_balance`. The docs do not state whether `balance` already excludes locked funds; the phrasing *"Locked balance is the balance currently being used by an open order"* implies they are disjoint. UNVERIFIED. Experiment: read balances, place a far-from-market limit buy for a known notional, re-read, and check whether `balance` fell by that notional while `locked_balance` rose by it.
- No pagination, no currency filter. Returns everything.
- **This is the only funding-currency source of truth.** Requirement 7 (INR sometimes, USDT sometimes) is answered here: read `currency` and never convert. See 03-domain-model...
- No fee tier is exposed: FAQ *"Can I get my fee tier via APIs - We currently don't have this available on our APIs"* (V-doc 14050-14052). Fee rates arrive only per-order as `maker_fee`/`taker_fee`.

#### F6.2 `POST /exchange/v1/users/info`

Request: `{ "timestamp": <ms> }`.

Response: array with a single object.

| Field | Type | Meaning |
| --- | --- | --- |
| `coindcx_id` | string (UUID in sample) | *"coindcx_id is the user id"* |
| `first_name`, `last_name`, `mobile_number`, `email` | string | account holder PII |

- Use: **verify at onboarding that a newly added API key belongs to a distinct account**, by storing a hash of `coindcx_id`. Two "accounts" in one Tradex group that share a `coindcx_id` are the same exchange account and would double-trade the same balance. This is a cheap, high-value guard.

### F8. Order endpoints

All 11 endpoints, exhaustively (grep-verified: there are exactly 11 `exchange/v1/orders/*` paths in the docs, and **no** spot order-history/list endpoint).

#### F8.1 `POST /exchange/v1/orders/create`

Request (V-doc 2183-2223):

| Param | Required | Type in samples | Notes |
| --- | --- | --- | --- |
| `market` | Yes | string | `coindcx_name`, e.g. `BTCINR`. *"The trading pair"* |
| `total_quantity` | Yes | **number** in every sample | *"Quantity to trade"* - in the **target** asset. The only sizing input the API accepts |
| `side` | Yes | string | `buy` / `sell` |
| `order_type` | Yes | string | `market_order` / `limit_order` |
| `price_per_unit` | No | number **or** string (both appear in official samples: `0.03244` and `"0.03244"`) | *"Price per unit (not required for market order)"*. Required in practice for `limit_order` |
| `client_order_id` | No | string | *"Must be unique per order for each user. Reusing an existing client_order_id will be rejected."* |
| `timestamp` | Yes | number | ms (samples). Table example `1524211224` is a 10-digit seconds value - inconsistent |

- `ecode` is **not** a parameter of single create (it is only in the enum table and in `create_multiple`). `market` alone identifies the venue because `coindcx_name` is globally unique (V-live).
- Documented ceiling: *"You can only have a maximum of 25 open orders at a time for one specific market"* (V-doc 2177). This is per account per market. A 100-account group is unaffected (each account has its own book), but a strategy that ladders many limits on one market inside one account is.
- No `time_in_force` request param. No `quote_quantity` / `notional` / `amount` param of any kind - grep over the whole docs file finds `total_quantity` as the sole spot quantity field.

Response: `{ "orders": [ <order object> ] }` - an **array wrapper even for a single order**. Field-by-field meanings are in F10.

Discrepancies in the documented response (all V-doc):
- The response-parameter table documents a `pair` field (*"Internal pair identifier (e.g. KC-BTC_USDT)"*, line 2304) that appears in **none** of the response samples.
- Every sample shows `"source": "web"` and a `client_order_id` in CoinDCX's own web format (`09c60ff5b9894771b4a8bb753d015ae3_1783342068944297474`, 52 chars) rather than the `2022.02.14-btcinr_1` value the sample request sent. The samples were captured from web-originated orders. Therefore: that the API **echoes** our `client_order_id` is UNVERIFIED-by-sample, though the field description (*"It's provided while placing order by the user"*) states it. Experiment: place one order with `client_order_id: "tradex-probe-001"` and read the create response and `orders/status`.
- Those web ids are 52-54 characters, but the FAQ says *"The maximum allowed length is 36 characters"* (V-doc 14015). Either the limit is unenforced or the FAQ is stale. Design to <=36.
- `client_order_id` charset is never specified. The official examples use hex, digits, `_`, `.` and `-`. Stay in `[A-Za-z0-9._-]`.

#### F8.2 `POST /exchange/v1/orders/create_multiple`

Request: `{ "orders": [ <up to 10 order objects> ] }`. Each element takes the same fields as F8.1 **plus a required `ecode`**, and each element carries its own `timestamp` (V-doc 2341-2361, 2487-2541).

| Constraint | Value (verbatim) |
| --- | --- |
| markets | *"Multiple ordering is only supported for CoinDCX INR markets. Set ecode parameter to I."* |
| batch size | *"Maximum 10 orders per request."* |
| `client_order_id` | *"Must be unique for every order in the array"* |

Response: `{ "orders": [ ... ] }`, same object shape.

Load-bearing consequences:
- This batches orders for **one API key**, i.e. **one exchange account**. It cannot span accounts, because each account signs with its own secret. **A group trade is therefore N separate HTTP calls and cannot be atomic.**
- It is unusable for any USDT-quoted market (INR only), which is half of requirement 7.
- Per-element partial failure semantics are **not documented**: if 3 of 10 are illegal, is the whole request rejected or are 7 accepted? The response sample shows only 1 order for a 2-order request, which suggests per-element results but proves nothing. UNVERIFIED. Experiment: submit 2 orders on an INR market, one legal and one with `total_quantity: 0`, and record whether the legal one is placed and how the illegal one is reported.
- Recommendation: do not use `create_multiple` in v1. Single `create` per account gives one intent to one HTTP call to one row, which is what "no lost order" needs.

#### F8.6 `POST /exchange/v1/orders/trade_history` (account trades)

| Param | Required | Notes (verbatim) |
| --- | --- | --- |
| `limit` | No | *"(Integer) Max records to fetch. Default: 500. Maximum: 500."* |
| `from_id` | No | *"Trade ID after which you want the data. If not supplied, trades in ascending order will be returned"* |
| `sort` | No | *"Specify asc or desc ... default: asc"* |
| `from_timestamp` | No | ms; *"Timestamp after which you want the data"* |
| `to_timestamp` | No | ms; *"Timestamp before which you want the data"* |
| `symbol` | No | `coindcx_name`; *"If not supplied, trades from all symbols will be returned"* |
| `timestamp` | Yes | ms |

Response: array of trade objects.

| Field | Kind | Type | Meaning |
| --- | --- | --- | --- |
| `id` | identity | **number** | trade id; the cursor for `from_id` |
| `order_id` | identity | **string** of digits | joins to order `id` (also a string) |
| `side` | enum | string | `buy` / `sell` |
| `quantity` | QUANTITY | number | target asset filled on this trade |
| `price` | PRICE | number | base per target |
| `fee_amount` | NOTIONAL | number | fee for this trade, in the **base** currency |
| `ecode` | enum | string | `I` etc. |
| `symbol` | identity | string | `coindcx_name` in the sample (`USDTINR`) |
| `timestamp` | time | number | ms |

- **This is the reconciliation spine.** `symbol` is optional, so with `sort: asc` plus a persisted `from_id` cursor it is an account-wide, monotonic, gap-free feed of everything that actually executed - including fills on orders Tradex never placed (manual web trades) and fills on orders whose create response we lost.
- **No `client_order_id` on a trade.** Trades join to intents only via `order_id`, so the order row must be persisted with both `client_order_id` and the exchange `id` as soon as the id is known.
- `id` is a number here but order `id` is a string of digits. Do not compare across the two without normalising.
- UNVERIFIED: whether `symbol` returns `coindcx_name` or the upstream form on `KC`/`G` markets (`LYX-USDT` vs `LYXUSDT`). If it returns the upstream form, a naive join on symbol breaks for 284 markets. Experiment: execute one tiny trade on a `KC` market and inspect `symbol`.
- UNVERIFIED: `from_id` semantics with `sort: desc`. Always send `sort: asc`.
- Fee note (V-doc 13978-13980): *"the parameter fee returns the fee percentage charged on the transaction whereas the fee_amount parameter returns the absolute amount of fee charged in the base currency"*. So realised P&L must subtract `fee_amount` in the quote asset - never re-derive it from a percentage.

#### F8.8 `POST /exchange/v1/orders/cancel_all`

| Param | Required | Notes |
| --- | --- | --- |
| `market` | **Yes** | `coindcx_name` |
| `side` | No | omit to cancel both sides |
| `timestamp` | Yes | ms |

Verbatim usage note (V-doc 3482-3490): `{market: "SNTBTC", side: "sell"}` cancels all sell orders in that market; `{market: "SNTBTC"}` cancels all orders in that market.

- **Rate limit 30/60s** - by far the tightest budget in the API. A panic "cancel everything" across 100 accounts is 100 calls; if the limit is per-key it is fine, if per-IP it takes 200 seconds. This is the single most important unknown in F2 for the kill-switch design.

### F9. Lend / funding endpoints

Not used by Tradex v1. Recorded so that a future "idle capital earns yield" feature does not have to re-derive them, and because they share the account's balance with trading - a lend order locks funds that a group trade then cannot spend.

| Endpoint | Method | Request params | Response |
| --- | --- | --- | --- |
| `/exchange/v1/funding/fetch_orders` | POST | `timestamp` (number, Yes). Supports pagination (`page`, `size`) | array of lend orders |
| `/exchange/v1/funding/lend` | POST | `currency_short_name` (string, Yes), `amount` (number, Yes, *"Quantity to lend"*), `duration` (number, Yes, *"Time period ... in days"*), `timestamp` | array with the created lend order |

One shape is returned by `create`, `create_multiple`, `status`, `status_multiple`, `edit` and `active_orders`, with per-endpoint additions and one per-endpoint type change. Kind column: **PRICE** = base per target; **QUANTITY** = target asset; **NOTIONAL** = base asset amount; **RATE** = percent.

| Field | Kind | Type in samples | Meaning | Present on |
| --- | --- | --- | --- | --- |
| `id` | identity | **string of digits** | *"Now a positive numeric string. UUID format is no longer accepted."* | all |
| `client_order_id` | identity | string | *"It's provided while placing order by the user"* | all |
| `user_id` | identity | string of digits | *"Now numeric strings."* | `active_orders` only |
| `market` | identity | string | `coindcx_name` | all |
| `pair` | identity | string | documented (*"e.g. KC-BTC_USDT"*) but **absent from every sample** | documented on `create` |

| `side` | enum | string | `buy` / `sell` | all |
| `order_type` | enum | string | `limit_order` / `market_order` | all |
| `status` | enum | string | see F4 | all |

| `total_quantity` | QUANTITY | number | *"Quantity on the order"* | all |
| `remaining_quantity` | QUANTITY | number | *"Quantity remaining to be filled"* | all |
| `cancelled_quantity` | QUANTITY | number | *"Quantity cancelled on this order. 0 if not cancelled."* - defined in the socket docs, **absent from every spot REST sample** | UNVERIFIED on REST |
| `avg_price` | PRICE | number | *"Average executed price (0 until fills occur)"* | all |

| `locked_spot_balance` | flag | boolean | *"true if spot balance is locked"* | `active_orders` only |

| `trades` | array | **null** in every sample | element shape never documented | all |

Derived quantities - the API gives no field for any of these:

| Derived | Formula | Caveat |
| --- | --- | --- |
| filled quantity | `total_quantity - remaining_quantity` | if `cancelled_quantity` does appear on REST, subtract it too, or a partially-cancelled order reads as more filled than it is |
| executed notional | sum of `quantity * price` over `orders/trade_history` rows with this `order_id` | `avg_price * filled` is an approximation; use it only for display, never for P&L |
| realised fee | sum of `fee_amount` over the same trade rows | the order-level `fee_amount` is a running total and is safe too; do not mix the two sources |

There is no `executed_quantity`, no `executed_notional`, no `cost` and no `is_working` field. Anything the analytics tracks need must be derived here and stored.

### F11. Errors

Global HTTP codes (V-doc 14077-14111): `400` *"Bad Request -- Your request is invalid."*, `401` *"Unauthorized -- Your API key is wrong."*, `404` *"Not Found"*, `429` *"Too Many Requests -- You're making too many API calls"*, `500` *"Internal Server Error"*, `503` *"Service Unavailable -- We're temporarily offline for maintenance."*

FAQ adds (V-doc 13929-13936): *"In the case of API failure you get a 5xx error"* - `500` is *"a one-off error"*, `503` is *"a downtime at CoinDCX"*.

Live envelope shapes (V-live, 2026-09-03):

| Situation | HTTP | Body |
| --- | --- | --- |
| public param validation | 422 | `{"code":422,"errorCode":"BFF-SO-004","message":"interval must be one of [1m, 15m, 1h, 1d]","status":"error"}` |
| unknown pair | 422 | `{"code":422,"errorCode":"BFF-SO-004","message":"Invalid pair NOPE","status":"error"}` |
| no auth headers on `users/balances` | 401 | `{"code":401,"message":"Invalid credentials","status":"error"}` |
| no auth headers on `orders/status` | 401 | `{"code":401,"message":"You are not logged in","status":"error"}` |

- **422 is not in the documented code list** but is what public validation actually returns.
- `errorCode` is an undocumented structured namespace (`BFF-SO-004` seen on every market_data validation failure). It is **absent** on the 401 bodies, so the envelope is not uniform: branch on `code`, treat `errorCode` as optional, and never branch on `message` - two routes gave two different strings for the same failure.
- FAQ verbatim message strings worth matching defensively (V-doc 14053-14074): *"Invalid Request"*, *"Order type not allowed"*, *"Too Many Requests"*, *"This order cannot be cancelled"*, *"packet queue is empty, aborting"* (socket only).
- **There is no documented error table for any `orders/*` endpoint.** Rejection reasons are opaque strings. FAQ lists the causes without the wire text (V-doc 14017-14026): insufficient balance, rate limit hit, order type not available for the market, missing mandatory fields; and post-acceptance rejection because *"in case of market orders, the order value could go below the min notional value of the market"*.
- The adapter must therefore classify by HTTP code plus a small, versioned substring table, and default unknown failures to **indeterminate**, never to "failed". An indeterminate create is resolved by `orders/status` on the `client_order_id`, never by a retry.

## Design

### D1. The one honest sentence

"100% error free" is not achievable for a system that places real orders on a third-party exchange over the public internet. CoinDCX itself disclaims it - the API Terms state the API is provided *"WITHOUT WARRANTY OF ANY KIND"* and *"DOES NOT WARRANT THAT THE COINDCX API ... WILL BE SAFE, UNINTERRUPTED, ERROR FREE"*, with total liability capped at Rs 1,00,000 (V-doc 495, 503). Packets are lost, 500s happen, and an accepted order can be rejected asynchronously. What this contract *does* support, and what the adapter must therefore guarantee, is the five properties in the brief: no lost order, no duplicate order, no silent divergence, no wrong size, and partial group failure as a reported outcome. Everything below exists to deliver those five.

### D2. Order state machine over CoinDCX's verbatim strings

```
                          create accepted
   (our intent) --------------------------------> [init] --------> [open]
        |                                            |               |
        | 4xx/5xx/timeout                            |               +--> [partially_filled]
        v                                            |               |         |
  [INDETERMINATE] --status(client_order_id)--> (any of the above)     |         |
        |                                                            |         |
        +-- not found ---> [NEVER_PLACED] (safe to re-send same id)   |         |
                                                                     v         v
   terminal set:  [filled]   [cancelled]   [partially_cancelled]   [rejected]
```

- Open-equivalent (may still change): `init`, `open`, `partially_filled`.
- Terminal (cannot change): `filled`, `cancelled`, `partially_cancelled`, `rejected`.
- `INDETERMINATE` and `NEVER_PLACED` are **ours**, not CoinDCX's. Every accepted intent must reach one of the four terminal strings or be explicitly parked in `INDETERMINATE` with an alarm. That is the "no lost order" invariant, and it is enforceable only because `client_order_id` is a lookup key.
- `rejected` can arrive **after** acceptance (V-doc 14025), so a terminal-state watcher cannot stop polling at "accepted".

### D3. Idempotent create - the only safe sequence

```
1. compute size, legalise against markets_details          (D4)
2. cid  = "tdx-" + <short account ref> + "-" + <ulid>       (<= 36 chars, [A-Za-z0-9._-])
3. PERSIST intent row {cid, account, market, side, type, qty, price, state=SENDING}  <-- before any network I/O
4. body = hand-built JSON string; sig = HMAC-SHA256(body, secret)
5. POST /exchange/v1/orders/create with body verbatim
6a. 200 -> persist {exchange_id, status}, state=LIVE
6b. 4xx with a classifiable rejection -> state=REJECTED, record the verbatim message
6c. anything else (timeout, 5xx, unknown 4xx, connection reset) -> state=INDETERMINATE
       then loop, with backoff:  POST /exchange/v1/orders/status {client_order_id: cid}
         found      -> adopt its status, state=LIVE or terminal
         not found  -> state=NEVER_PLACED; re-sending the SAME cid is safe
         still error -> stay INDETERMINATE, alarm after N attempts; NEVER create again
```

Step 3 before step 5 is what makes "no lost order" true: a crash between 3 and 5 leaves a row whose resolution is a `status` lookup. A crash after 5 with no row would leave an order nobody owns, and F8 shows the exchange offers no way to enumerate it.

Two properties this leans on, and both need the F8.3 experiment before we ship: the exact "unknown client_order_id" response, and whether a duplicate `client_order_id` is rejected distinguishably. Until both are measured, the algorithm still holds - it just spends more polls.

### D4. Sizing and legality - the money-critical path

Inputs: `markets_details` row `M`, a reference price `P`, the requested size expressed as one of {quantity, notional, percent-of-allocated-capital}, and the account's allocated capital `C` **with its currency**.

```
0. assert M.base_currency_short_name == currency(C)          # never convert; refuse instead
1. notional N:
     quantity mode -> skip to 3
     absolute mode -> N = amount
     percent mode  -> N = C * pct / 100                      # exact decimal, no float
2. price P:
     limit_order  -> P = user limit price
     market_order -> P = best ask (buy) / best bid (sell) from market_data/orderbook
                     plus a slippage guard band; never from /exchange/ticker (cached)
3. raw quantity Q = N / P                                    # decimal division, no rounding yet
4. Q = floor_to_step(Q, M.step)                              # floor, never round: never overspend
5. Q = floor_to_decimals(Q, M.target_currency_precision)      # step and precision are independent
6. reject unless Q >= max(M.min_quantity, 10^-M.target_currency_precision)
7. reject unless Q <= (market ? M.max_quantity_market : M.max_quantity)
8. reject unless Q * P >= M.min_notional
9. reject unless M.min_price <= P <= M.max_price and decimals(P) <= M.base_currency_precision
10. reject unless order_type in M.order_types
11. emit body with Q and P as exact decimal literals
```

- **Floor, never round**, at steps 4 and 5. Rounding up on a percentage buy can exceed the allocated capital, and on a SELL ALL can exceed the held position and be rejected by the exchange.
- SELL sizing (requirement 5) reads the position from `users/balances` (`balance` for the target asset, excluding `locked_balance`), then runs the same steps 4-10. "SELL ALL" and "CLOSE POSITION" both floor to `step`, which means a dust remainder below one `step` is **unavoidable and must be reported**, not hidden.
- Every rejection at steps 6-10 is a per-account leg outcome, which is precisely the "partial group failure is first-class" requirement. The reason must name the constraint and the numbers.

### D5. Reconciliation - "no silent divergence"

Three independent loops per account, all cheap:

| Loop | Call | Cadence | Detects |
| --- | --- | --- | --- |
| open-order poll | `orders/status_multiple` on our non-terminal ids, 10 per call | seconds while any order is open | fills, cancels, async rejects |
| trade sweep | `orders/trade_history` with `sort: asc`, `from_id` cursor, no `symbol` | continuous, low rate | trades on orders we do not know about; fills whose create response we lost; the customer's manual trades |
| balance check | `users/balances` | after every group trade settles, plus periodically | drift between our modelled position and the exchange's |

A trade whose `order_id` is not in our order table is a divergence event: alarm, surface it, do not auto-correct. A `users/balances` figure that disagrees with our derived position by more than one `step` is a divergence event.

Sockets (see the websocket track) can replace the first loop's latency but not its authority: REST polling stays as the backstop, because a dropped socket is silent and this is real money.

## Failure modes

| Failure | Detection | Mitigation | Blast radius |
| --- | --- | --- | --- |
| `create` times out after the exchange accepted it | intent row stuck in `SENDING`/`INDETERMINATE` | resolve by `orders/status` on `client_order_id`; never re-create | one account leg; a blind retry would double the position |
| Duplicate order from a retry | two exchange ids for one `client_order_id` | one `client_order_id` per intent, generated once and persisted before send | one account leg, unbounded money |
| Client re-serialises the signed body differently | 401 on every authenticated call | build the body string once, sign those bytes, send them verbatim; assert body equals signedBody in the adapter | all trading blocked - loud, not silent |
| Timestamp skew exceeds CoinDCX's window | systematic auth/timestamp rejections | NTP-sync the host; measure the tolerance (F1 experiment); log server `Date` header drift | all trading blocked |
| Percentage size lands below `min_notional` or the precision floor | steps 6 and 8 of D4 reject pre-flight | refuse the leg with the numbers, or apply the chosen rounding policy | one account leg, reported |
| Market order exceeds `max_quantity_market` | step 7 of D4 | refuse, or split - owner decision; BTCINR caps at 0.0158 BTC | one account leg, reported |
| MARKET requested on a limit-only market | step 10 of D4 against `order_types` | refuse; 328 of 999 markets are affected | one account leg, reported |
| Float arithmetic corrupts a size | property test: every emitted body round-trips to the exact decimal computed | decimal type end to end; hand-built JSON literals; no `parseFloat` in the adapter | every leg of every trade, silently wrong |
| base/target confusion | unit test asserting `min_notional` is compared to a quote amount and `step` to a target quantity | one translation function at the boundary; never reuse CoinDCX field names in domain types | every order on every market |
| Wrong-currency sizing (INR capital against a USDT market) | step 0 of D4 | refuse; never convert (requirement 7) | one account leg |
| Async `rejected` after acceptance | terminal-state watcher keeps polling past acceptance | a 200 from `create` is not success; only a terminal status is an outcome | one leg; group exposure differs from intent |
| Partial group fill | per-leg terminal states aggregated at group level | report a per-account outcome table; never a single "success" | asymmetric group exposure - the headline product risk |
| 429 mid-fan-out | HTTP 429, or the `Too Many Requests` message | self-imposed token bucket at 16/s and 960/min per key; queue and preserve leg order; surface a delayed leg state | part of the group trades later, at a different price |
| Kill switch hits the `cancel_all` 30/60s limit | 429 on `cancel_all` | prefer `cancel_by_ids` (300/60s, 10 per call) for our own orders; reserve `cancel_all` for panic | slow cancellation while the market moves |
| `cancel_all` cancels orders we did not place | nothing in the response reports what it cancelled | require explicit confirmation naming the market; snapshot `active_orders` first | the customers unrelated orders destroyed |
| Divergence between our state and the exchange | trade sweep finds an unknown `order_id`; balances disagree by more than one `step` | alarm and surface; freeze new trades for that account until acknowledged | one account; its analytics are invalid until resolved |
| Lost order after losing our own database row | nothing can detect it - no order-history endpoint exists | write the intent row before the network call; back up the order log; the log is the system of record | unbounded and unrecoverable |
| CoinDCX 503 or scheduled downtime | 503 responses | circuit-break per account, park intents, never silently drop them | all trading paused |
| `markets_details` cache goes stale | refresh on a schedule; diff every refresh and alarm on constraint changes | re-validate against a fresh row when a leg is rejected for a size reason | mis-sized or refused legs |
| A trade `symbol` returns in upstream form on KC/G markets | reconciler cannot join it | join on `order_id`, never on symbol; run the F8.6 experiment before enabling KC/G | reconciliation false positives on 284 markets |
| Two Tradex accounts are the same exchange account | equal `coindcx_id` hash at onboarding | check `users/info` on every key add and refuse duplicates | double exposure while the group looks diversified |

## Open questions for Anand

**1. The API Terms may prohibit the product's core UI.** Clause 2.3(c), verbatim (V-doc 442):

> *"The User shall not redistribute, display, or disseminate the Market Data or any data, charts, analytics, research, or other works based on, referring to, or derived from the Market Data to any third party."*

A multi-tenant SaaS that shows CoinDCX-derived charts, group analytics and P&L to paying customers is arguably doing exactly that. Three ways out:

- get written permission or a data licence from CoinDCX
- render all charts from a third-party feed and never display CoinDCX market data
- ship single-tenant / self-hosted, so there is no third party

Related clauses: 6.4 warrants that the user holds any licence required for algorithmic trading; 6.6 requires records be kept **5 years** after termination; 9 caps CoinDCX liability at Rs 1,00,000.

**2. Do we require IP-bound API keys?** There is no read-only or trade-only key scoping (V-doc 13912-13919), so a leaked key is full trading authority plus wallet transfers. IP binding is the only mitigation, and it forces a fixed egress IP - which constrains hosting and horizontal scaling. Bind, or stay elastic with a larger blast radius?

**3. `max_quantity_market` will block large market buys.** BTCINR allows a market order of only 0.0158 BTC, about Rs 1.27 lakh at Rs 8.03M per BTC (V-live). A 20% size on a Rs 10,00,000 account exceeds it. Refuse the leg, or auto-split into sequential market orders at successively worse prices?

**4. Sub-minimum legs.** INR `min_notional` is Rs 100, and BTCINR's quantity grid makes the smallest legal order about Rs 160. When a percentage size lands under it: refuse and report, round up to the minimum, or skip silently? Recommendation: refuse and report.

**5. Are illegal legs allowed to stop the whole group?** All-or-nothing pre-flight, or best-effort? Recommendation: all-or-nothing on **validation** failures, which are knowable before any money moves, and best-effort on **execution** failures, which are not.

**6. Mixed-currency groups.** If one group holds INR-funded and USDT-funded accounts, one logical trade becomes two markets (BTCINR and BTCUSDT) with different prices, precisions and minimums. Allow it as two sub-trades, or require single-currency groups? Requirement 7 forbids converting either way.

**7. Who owns the keys operationally?** Holding many customers' keys makes Tradex a high-value target with custodial-adjacent risk, and CoinDCX states plainly that keys are unscoped and interchangeable. Confirm the owner accepts that, and whether customers will accept IP binding. Feeds 07-api-key-security.md.

**8. Which experiments get a funded test account, and when?** Eleven load-bearing facts in this document are UNVERIFIED and only a live key settles them. They are cheap - a few rupees on USDTINR - but they must happen before the order path is trusted. List in Phase hints.
